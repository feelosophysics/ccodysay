# 5. 평가문항 및 모범 답안 (Educational Model Answers)

본 답안은 RDBMS의 관계형 대수학, 논리적 쿼리 처리 단계, 데이터 무결성 제약조건의 전파, 그리고 디스크 I/O 최적화를 위한 인덱스 메커니즘 등 데이터베이스 엔진 내부의 동작 원리를 기반으로 기술되었습니다.

### 항목 1: 요구사항 검증 및 정합성 체크 (Validation & Integrity Check)

* **최소 4개 테이블이 존재하고, 각 테이블에 PK가 정의되어 있는가?**
  * **모범 답안**:
    현재 설계 및 구축된 도서 대여 데이터베이스 (schema.sql) 에는 총 4개의 테이블이 정의되어 있으며, 각 테이블은 개체 무결성(Entity Integrity)을 규정하기 위해 인위적 대리키(Surrogate Key)를 기본키(PK, Primary Key)로 선언하고 있습니다.
    1. **CATEGORY 테이블**: `id` 컬럼 (`INTEGER PRIMARY KEY AUTOINCREMENT`)
    2. **MEMBER 테이블**: `id` 컬럼 (`INTEGER PRIMARY KEY AUTOINCREMENT`)
    3. **BOOK 테이블**: `id` 컬럼 (`INTEGER PRIMARY KEY AUTOINCREMENT`)
    4. **RENTAL 테이블**: `id` 컬럼 (`INTEGER PRIMARY KEY AUTOINCREMENT`)
    
    * **학술적/원리적 분석 (개체 무결성과 SQLite 내부 메커니즘)**:
      * **개체 무결성(Entity Integrity)**: 관계 데이터 모델에서 기본키는 테이블 내의 임의의 튜플(Tuple)을 고유하게 식별할 수 있는 유일성(Uniqueness)과 최소성(Minimality)을 만족하는 속성의 집합입니다. 개체 무결성 제약에 따라 PK는 어떠한 경우에도 빈 값(NULL)을 가질 수 없으며, 중복되어서도 안 됩니다. 이를 통해 현실 세계의 고유한 엔티티가 테이블 내부에서 유일한 인스턴스로 식별됨을 보장합니다.
      * **SQLite의 Clustered Index 구조와 RowID**: SQLite에서 `INTEGER PRIMARY KEY`를 선언하면 해당 컬럼은 단순히 기본키 역할을 수행할 뿐만 아니라, B-Tree의 단말 노드에 데이터 행 자체를 직접 담는 **RowID(64-bit Signed Integer)**의 직접적인 별칭(Alias)이 됩니다. 이를 통해 PK 기반 검색 시 별도의 인덱스 테이블을 거치지 않고 데이터 페이지로 곧바로 도약하는 클러스터형 인덱스(Clustered Index) 구조의 혜택을 얻어 $O(1)$에 근사하는 매우 신속한 물리적 스캔 속도를 냅니다.
      * **AUTOINCREMENT의 상태 관리 매커니즘**: `AUTOINCREMENT`가 명시되면 SQLite 엔진은 시스템 메타데이터 테이블인 `sqlite_sequence`를 활성화하여 현재까지 발행되었던 최대 ID 값을 지속적으로 기록합니다. 이 메커니즘 덕분에 기존에 생성되었다가 물리적으로 삭제된 ID(예: 회원 정보 삭제로 날아간 11번 ID)가 향후 새로운 데이터 삽입 시 재사용되지 않도록 영구히 보장하며, 비즈니스 기록의 히스토리 추적성 및 정합성을 엄격하게 방어합니다.

* **FK를 사용한 1:N 관계가 최소 2개 이상 존재하고, 없는 값 참조가 실제로 막히는가?**
  * **모범 답안**:
    도메인의 비즈니스 관계를 매핑하기 위해 총 3개의 외래키(FK, Foreign Key) 제약조건이 구성되어 있으며, 실시간 제약조건 검사를 통해 **참조 무결성(Referential Integrity)**을 견고하게 강제하고 있습니다.
    1. **CATEGORY (1) : BOOK (N)**: `BOOK.category_id` -> `CATEGORY.id` 참조 (`ON DELETE RESTRICT`)
    2. **MEMBER (1) : RENTAL (N)**: `RENTAL.member_id` -> `MEMBER.id` 참조 (`ON DELETE CASCADE`)
    3. **BOOK (1) : RENTAL (N)**: `RENTAL.book_id` -> `BOOK.id` 참조 (`ON DELETE RESTRICT`)
    
    * **참조 거부 메커니즘 물리 검증 (bonus_queries.sql):
      SQLite는 기본 하위 호환성을 유지하기 위해 외래키 제약 검사가 꺼져 있으므로, 반드시 세션 최초 접속 시 `PRAGMA foreign_keys = ON;` 명령을 수행하여 무결성 감시 엔진을 활성화해야 합니다. 이 설정 하에서 없는 값을 참조할 때의 물리적 거부 메커니즘은 다음과 같습니다.
      * **미등록 회원(member_id=999)의 대여 기록 추가 시도**:
        ```sql
        INSERT INTO RENTAL (id, member_id, book_id, rental_date, status) 
        VALUES (999, 999, 1, '2026-05-24', 'RENTED');
        ```
        이 쿼리가 진입하면 RDBMS의 제약 조건 처리기는 부모 테이블인 `MEMBER`에서 `id=999` 행이 실재하는지 즉시 인덱스 탐색을 수행합니다. 해당 행의 부재가 인지되는 순간, 트랜잭션 엔진은 작업을 즉각 중단하고 `Result: FOREIGN KEY constraint failed` 예외를 발생시키며 쓰기 작업을 완전히 롤백(Rollback)합니다.
      * **미등록 카테고리(category_id=100)로 도서 등록 시도**:
        ```sql
        INSERT INTO BOOK (id, title, category_id, author, price, published_date)
        VALUES (999, '존재할 수 없는 책', 100, '미상', 15000, '2026-01-01');
        ```
        이 또한 부모 릴레이션인 `CATEGORY`에 존재하지 않는 도메인 값 `100`을 FK 컬럼에 삽입하려 하므로 참조 무결성을 위해 엔진 단에서 강력하게 거부됩니다. 이 방어 장치가 존재하기 때문에 누구에게 대여되었는지 알 수 없는 '고아 트랜잭션 데이터'나 분류 체계가 붕괴된 '고아 도서 데이터'의 누적을 원천적으로 봉쇄할 수 있습니다.

* **각 테이블에 최소 10행 이상의 샘플 데이터가 입력되어 있는가?**
  * **모범 답안**:
    샘플 데이터 적재 파일 (data.sql)을 통해 각 테이블에 풍부한 테스트 데이터를 구축하였으며, 실무 시나리오(장기 대여, 다독 회원, 연체 건 등)를 온전히 반영하여 쿼리 성능 분석이 가능한 상태로 채워져 있습니다.
    - `CATEGORY` 테이블: 총 10행 (1~10번 장르)
    - `MEMBER` 테이블: 총 11행 (1~10번 일반 회원, 12번 휴면 회원)
    - `BOOK` 테이블: 총 11행 (1~11번 도서 정보)
    - `RENTAL` 테이블: 총 15행 (1~15번 도서 대여 트랜잭션 기록)
    
    * **학술적/원리적 분석 (외래키 종속 관계에 따른 데이터 적재 순서 계층)**:
      외래키 제약조건 하에서는 부모 테이블의 데이터가 먼저 존재해야만 자식 테이블이 이를 참조할 수 있습니다. 따라서 스크립트 작성 시 **참조 종속성 계층(Referential Dependency Hierarchy)**에 맞춰 엄격한 물리적 인서트 순서를 지켜야 합니다.
      1. **1계층 (기저 마스터 데이터)**: `CATEGORY`, `MEMBER` (스스로 외래키를 갖고 있지 않으며 다른 테이블에 의해 참조당하는 독립 엔티티)
      2. **2계층 (1차 종속 데이터)**: `BOOK` (책이 삽입되려면 반드시 유효한 장르 ID를 참조해야 하므로 `CATEGORY`가 선적재되어 있어야 함)
      3. **3계층 (2차 종속 데이터)**: `RENTAL` (대여 거래 정보는 빌리는 주체인 `MEMBER`와 빌려주는 대상인 `BOOK`의 존재를 전제로 성립되므로, 최종 단계에 적재되어야 함)
      이 종속 관계를 무시하고 `RENTAL` 데이터를 먼저 인서트하려고 시도하면 부모 노드의 실재 여부 검사를 통과하지 못해 에러가 발생하게 됩니다.

* **기본 조회(4개), 조인(4개), 집계(3개), 서브쿼리(1개), 수정/삭제(2개), 인덱스(1개)를 포함한 쿼리 15개가 작성되어 있는가?**
  * **모범 답안**:
    작성된 (queries.sql) 파일에는 각 요구 사양에 완벽하게 부합하며, 정교한 SQL 엔진 최적화를 체험할 수 있는 총 16개의 논리 쿼리가 완비되어 있습니다.
    - **기본 조회(4개)**: Query 1 (MEMBER 가입일 순 조회), Query 2 (BOOK 고가 도서 내림차순 필터링), Query 3 (MEMBER 패턴 매칭 및 LIMIT 기반 페이징 최적화), Query 4 (CATEGORY 명칭 사전순 정렬)
    - **조인 조회(4개)**: Query 5 (RENTAL-MEMBER-BOOK 3자 내부조인), Query 6 (특정 회원의 1:N 이력 조회), Query 7 (전체 도서 대상의 누적 대여 횟수 LEFT JOIN 통계), Query 8 (회원 기준의 실시간 대여 현황 LEFT JOIN 분석)
    - **집계 및 그룹화(3개)**: Query 9 (카테고리별 도서 수 및 평균 가격 GROUP BY), Query 10 (회원별 누적 대여 횟수 및 총 가격 가치 합산 GROUP BY), Query 11 (RENTAL 상태 분포 집계 GROUP BY)
    - **서브쿼리 조회(2개)**: Query 12 (전체 평균 도서가 대비 초과 도서 필터링 - 스칼라 비교 서브쿼리), Query 13 (대여 이력이 전무한 휴면 회원 추출 - 상관 `NOT EXISTS` 서브쿼리)
    - **수정 및 삭제(2개)**: Query 14 (14일 이상 장기 대여 건의 'OVERDUE' 일괄 갱신), Query 15 (임시 데이터 추가 후 회원 삭제를 통한 `ON DELETE CASCADE` 물리적 정화 검증)
    - **인덱스 적용(1개)**: Query 16 (`idx_rental_status` 생성을 통한 B-Tree 성능 고도화)

* **각 쿼리의 실행 결과가 스크린샷 또는 텍스트로 첨부되어 있는가?**
  * **모범 답안**:

### 항목 2: 데이터베이스 설계 및 스키마 선정 이유 (Schema Design Rationale)

* **테이블을 왜 이렇게 나눴는지, 각 테이블의 역할을 말할 수 있는가?**
  * **모범 답안**:
    데이터의 유기적 분할은 디스크 공간 절약뿐만 아니라 비즈니스 로직 변경 시 데이터의 무결성 붕괴(이상 현상)를 방지하는 중추적 수단입니다. 본 설계는 OLTP의 특성에 맞춰 관계형 모델의 정규화 이론을 충실히 반영했습니다.
    1. **CATEGORY (분류 엔티티)**: 도서 장르라는 도메인 메타데이터를 통합 관리합니다. 장르 이름이 바뀌거나 신규 장르가 추가되는 등 도메인의 논리적 변형이 도서 엔티티와 물리적으로 결합되지 않도록 완전히 분리하였습니다.
    2. **MEMBER (주체 엔티티)**: 도서관의 이용 주체인 회원들에 대한 마스터 데이터셋입니다. 회원의 가입, 메일 관리 등 회원 고유의 생명주기를 담당합니다.
    3. **BOOK (기준 정보 엔티티)**: 보유 도서 목록과 개별 도서의 서지 정보를 저장합니다. 한 권의 책은 하나의 분류에 온전히 소속되므로 `CATEGORY` 테이블과 1:N 관계를 맺습니다.
    4. **RENTAL (트랜잭션 엔티티)**: "회원이 도서를 대여/반납하는 구체적 사건"을 기록하는 테이블입니다. 회원과 도서의 논리적 다대다(M:N) 매핑 관계를 연결해 주는 교차 테이블(Intersection Table)이기도 합니다.
    
    * **학술적/원리적 분석 (정규화 단계와 이행적 종속 방지)**:
      * **제1정규형(1NF)**: 모든 컬럼에 다중값(Multi-valued)이나 중복 그룹이 배제된 단일 원자값(Atomic Value)만 들어가므로 충족되었습니다.
      * **제2정규형(2NF)**: 기본키가 복합키가 아닌 단일 인공 정수 키(`id`)로 정의되었기에, 기본키의 일부분에 종속되는 부분 함수 종속(Partial Functional Dependency)이 존재하지 않아 자동으로 만족합니다.
      * **제3정규형(3NF)**: 기본키가 아닌 일반 컬럼이 다른 일반 컬럼을 결정자로 삼아 이행적으로 종속되는 현상(이행적 함수 종속, Transitive Functional Dependency)을 분리합니다. 만약 `BOOK` 테이블에 `category_id`뿐만 아니라 `category_name`까지 함께 기재되어 있다면, $id \rightarrow category\_id \rightarrow category\_name$ 이라는 이행적 함수 종속이 성립되어 **수정 이상(Update Anomaly)**이 발생하게 됩니다. '컴퓨터과학' 장르명을 'IT융합과학'으로 수정하기 위해 수만 권의 도서 레코드를 UPDATE해야 하는 상황을 피하기 위해, `category_id`만을 남기고 장르명은 `CATEGORY`라는 독자 릴레이션으로 추출하여 완전한 3NF 구조를 성립시켰습니다.

* **FK로 연결된 1:N 관계가 실제 도메인에서 어떤 의미인지 예시를 들어 보여줄 수 있는가?**
  * **모범 답안**:
    1:N 관계는 부모 테이블의 단일 식별자가 자식 테이블의 여러 인스턴스에 걸쳐 매핑될 수 있는 비즈니스적 소속 또는 거래 누적 관계를 의미합니다.
    1. **MEMBER (1) : RENTAL (N)**:
       - **도메인적 의미**: 한 명의 회원은 가입 기간 동안 도서관을 활발히 이용하며 여러 번의 대여 거래를 누적해서 발생시킬 수 있습니다.
       - **실제 데이터 예시**: 회원의 고유 PK인 `MEMBER.id = 1`('이영희')은 `RENTAL` 테이블 내에서 `member_id = 1`을 가지는 총 3건의 대여 데이터 행(id=1, 2, 13)을 거느리게 됩니다. 이영희의 개인 신상정보는 유일무이하지만, 그녀가 생성한 거래 기록은 복수 개가 존재하는 1:N 대여 이력을 투명하게 사상합니다.
    2. **BOOK (1) : RENTAL (N)**:
       - **도메인적 의미**: 하나의 동일한 서적 개체는 대여와 반납을 반복하여 역사적으로 여러 대여 건에 기여할 수 있습니다.
       - **실제 데이터 예시**: `BOOK.id = 3`('코스모스') 도서는 RENTAL 테이블에서 `book_id = 3`인 2건의 기록(김철수의 연체 대여건 id=3, 임영웅의 정상 반납건 id=12)과 논리적으로 이어집니다.
    3. **CATEGORY (1) : BOOK (N)**:
       - **도메인적 의미**: 하나의 도서 카테고리(장르) 하위에는 동일 장르에 귀속되는 다양한 도서들이 소속될 수 있습니다.
       - **실제 데이터 예시**: `CATEGORY.id = 1`('컴퓨터과학') 카테고리 내부에는 `category_id = 1`로 명시된 도서 '밑바닥부터 시작하는 딥러닝(id=1)', '클린 코드(id=2)', 'Java의 정석(id=11)' 등이 그룹을 이룹니다.

* **컬럼 타입(TEXT, INTEGER, DATE 등)을 왜 그렇게 선택했는지 설명할 수 있는가?**
  * **모범 답안**:
    타입 선정은 데이터의 저장 공간 최적화와 함께, 데이터 진입 단계에서 올바른 도메인 값만을 걸러내는 **도메인 무결성(Domain Integrity)**을 형성하는 일차 관문입니다.
    1. **id (INTEGER PRIMARY KEY AUTOINCREMENT)**: 64비트 정수 식별자로써 고속의 인덱스 비교 연산을 보장하며, AUTOINCREMENT 상태 값을 통해 유일무이함을 보장받습니다.
    2. **name, title, email, phone (VARCHAR(N))**: 
       SQLite는 동적 타입 시스템(Dynamic Affinity)을 취해 실제 저장 시에는 dynamic TEXT로 취급하지만, SQL 스키마 수준에서 이메일 100자, 도서명 200자 등 표준 `VARCHAR(N)` 명세를 표기하여 협업 개발자에게 명확한 필드 가이드를 제공하고 이기종 RDBMS로의 마이그레이션 호환성을 충족시켰습니다.
    3. **price (INTEGER + CHECK 제약조건)**: 도서 가격은 정수로 소수점 오차가 발생하지 않도록 `INTEGER`로 지정했으며, 도메인 제약 `CHECK (price >= 0)`를 추가해 입력 부주의로 인한 '음수 가격'이라는 비논리적 데이터가 입력되는 것을 원천 차단했습니다.
    4. **dates (DATE)**: 가입일, 대여일, 반납일 등은 날짜 형태를 유지해야 하므로 `DATE` 타입으로 지정했습니다. 내부적으로 ISO-8601 포맷 문자열로 저장되어 문자열 정렬 순서와 실제 날짜 흐름 순서가 완벽히 대응하며, `julianday()` 등 내장 함수와 부드럽게 연동되어 정밀한 날짜 간 연산이 가능합니다.

* **인덱스를 어떤 컬럼에 걸었고, 왜 그 컬럼이어야 하는지 이유를 대답할 수 있는가?**
  * **모범 답안**:
    본 프로젝트에서는 대여 트랜잭션 기록 테이블인 `RENTAL`의 `status` 컬럼에 단일 컬럼 인덱스인 `idx_rental_status` (queries.sql:L351)를 설정하였습니다.
    * **인덱스 대상 컬럼 선정의 전략적 당위성 (선택도와 쿼리 프로파일링)**:
      1. **집중적인 비즈니스 쿼리 빈도**: 도서관 관리 소프트웨어에서 가장 자주 기동되는 데일리 화면은 "현재 미반납 상태인 책(RENTED, OVERDUE)"을 표시하는 대시보드입니다. 따라서 `WHERE status IN ('RENTED', 'OVERDUE')` 필터 조건이 하루 수천 번 실행됩니다.
      2. **Full Table Scan ($O(N)$)의 치명적 한계 극복**: 인덱스가 존재하지 않는다면 데이터베이스 엔진은 매번 조건에 부합하는 몇십 건의 미반납 레코드를 찾기 위해, 디스크 스토리지로부터 RENTAL 테이블 전체 행을 끝까지 로드해와 검사하는 테이블 풀 스캔(Full Table Scan)을 돌려야 합니다. 이는 데이터가 수백만 건으로 증식할 시 심각한 I/O 병목을 초래합니다.
      3. **B-Tree Range Scan ($O(\log N)$) 최적화**: `status` 컬럼에 인덱스를 걸면, SQLite는 `status` 필드 값을 Key로 삼아 정렬된 **Balanced B-Tree** 구조를 물리 메모리/디스크 영역에 추가로 생성합니다. 검색 요청 시 루트 노드부터 단말 노드까지 단 몇 차례의 탐색($O(\log N)$)으로 조건에 부합하는 데이터 번지들(RowIDs)을 정확하게 추적한 뒤 해당 레코드 페이지만 선별하여 디스크 I/O를 일으킵니다 (Index Range Scan).

### 항목 3: 데이터 모델 및 SQL 연산의 이해 (Relational Model & SQL Operators)

* **데이터베이스가 엑셀과 무엇이 다른지, 왜 테이블을 나눠서 저장하는지 비교하며 설명할 수 있는가?**
  * **모범 답안**:
    엑셀은 시각적 표현과 소량의 임의 분석에 우수하지만, RDBMS는 데이터의 완벽한 무결성과 영속성, 그리고 대규모 트랜잭션의 안전한 처리에 특화된 전용 시스템입니다.

    * **스프레드시트 (Excel) 대비 RDBMS의 결정적 기술적 차이**:
      1. **데이터 정합성 통제**: 엑셀 시트는 셀 단위로 자유로운 값 입력이 허용되므로 날짜 칸에 텍스트가 들어가도 막을 수 없어 품질이 쉽게 오염됩니다. 반면 RDBMS는 강력한 스키마 타입과 도메인 제약조건을 데이터가 영구 저장되는 물리 저장소 직전에 배치하여 부적절한 데이터 침입을 절대 불허합니다.
      2. **동시성 제어 (Concurrency Control) 및 락킹**: 엑셀 파일을 공유 폴더에 두면 여러 명의 관리자가 동시에 도서 반납을 반영할 때 최종 수정자만 덮어쓰여 이전 입력이 실종되는 '갱신 분실(Lost Update)'이 일어나고 파일이 자주 잠깁니다. RDBMS는 레코드 락(Row-level Lock)과 다중 버전 동시성 제어(MVCC)를 지원하여 수천 명이 동시에 도서를 빌리고 반납해도 한 치의 혼선 없이 병렬로 트랜잭션을 격리해 줍니다.
      3. **ACID 트랜잭션의 완벽 보장**: 정전이나 시스템 장애 시 엑셀은 파일이 훼손되거나 중간 작업이 완전히 파괴됩니다. RDBMS는 원자성(Atomicity), 일관성(Consistency), 격리성(Isolation), 지속성(Durability)을 규정하는 트랜잭션 규격을 철저히 고수하여, 데이터 변경 로그(Write-Ahead Log)를 디스크에 선반영하므로 시스템 재시작 시 장애 전 상태로 한 방에 복구해 냅니다.
      
    * **테이블을 나누어 분리 저장(정규화)하는 3대 당위성**:
      * **수정 이상 방지**: 한 테이블에 카테고리를 합쳐 놓으면 특정 카테고리명이 변경될 때 수만 행을 업데이트해야 하며, 도중에 멈추면 데이터가 불일치해집니다. 나누어두면 1행의 부모 값만 수정하면 끝납니다.
      * **삽입 이상 방지**: 만약 도서와 카테고리가 묶여 있다면 신규 장르 등록 시 아직 등록될 도서가 없으므로 도서 관련 필드에 전부 의미 없는 임시 NULL 값을 넣거나 행 추가 자체가 원칙적으로 거부됩니다.
      * **삭제 이상 방지**: 특정 카테고리에 속한 유일한 책을 폐기할 때, 테이블이 나뉘지 않았다면 그 책을 DELETE 하는 순간 해당 장르의 존립 정보 전체가 세상에서 영원히 삭제되는 심각한 정보 손실이 발생합니다.

* **PK와 FK의 역할과 1:N 관계의 데이터 연결 메커니즘**:
  * **모범 답안**:
    - **PK (기본키)**: 엔티티의 각 인스턴스(행)를 절대적으로 고유 식별하게 해주는 속성입니다. 중복을 막고 NULL을 제거해 데이터의 최소 단위 정체성을 구현합니다.
    - **FK (외래키)**: 다른 테이블의 PK 값을 참조하여 데이터의 연결고리를 선언합니다. 이를 통해 자식 테이블에 들어갈 수 있는 데이터 도메인을 부모 테이블의 PK 값들로 강력히 한정합니다.
    - **1:N 관계 데이터 연결 작동 원리 (물리 매핑 관점)**:
      `BOOK`과 `CATEGORY`를 연결할 때, `BOOK.category_id`에 저장되는 값은 단순한 숫자가 아니라 부모 테이블인 `CATEGORY`의 `id` 컬럼으로 이어지는 **논리 포인터** 역할을 합니다. 쿼리 파서가 이 관계를 해석하여 조인을 가동하면, DB 엔진은 두 테이블의 해시 맵 또는 인덱스 노드를 순회하며 `BOOK.category_id`와 `CATEGORY.id`가 일치하는 주소 공간을 찾아 메모리상에서 두 튜플을 가로로 길게 접합시킵니다.

* **INNER JOIN과 LEFT JOIN의 차이를 실행 결과를 보며 짚어줄 수 있는가?**
  * **모범 답안**:
    - **INNER JOIN**: 두 테이블 간의 조인 조건을 모두 완벽하게 충족하는 교집합($A \cap B$) 행만 통과시킵니다. 한쪽이라도 매칭되는 짝이 존재하지 않는 행은 최종 출력에서 제외됩니다.
    - **LEFT JOIN**: 왼쪽 기준 테이블의 모든 행을 결과 셋에 온전히 유지하면서, 오른쪽 테이블의 데이터를 우측에 병합시킵니다. 이때 매칭되는 짝이 없는 오른쪽 필드들은 엔진이 자동으로 NULL을 배정하여 반환합니다.
    - **통계 쿼리 (queries.sql:L151-158) 기반 실증 비교**:
      도서관이 보유한 전 도서의 누적 대여 통계를 산출하기 위해 `BOOK`과 `RENTAL` 테이블을 조인하는 상황입니다.
      * **LEFT JOIN 실행 결과**:
        ```
        book_id | book_title  | total_rentals
        --------+-------------+--------------
        11      | Java의 정석  | 0
        ```
        이처럼 단 한 번도 대여되지 않은 비인기 도서인 'Java의 정석(id=11)'이 `total_rentals = 0`으로 화면에 정확하게 집계됩니다. `LEFT JOIN`이 왼쪽 테이블인 `BOOK`을 강제로 보존하고, 매치되지 않은 `RENTAL.id` 자리에 NULL을 채워넣은 후 `COUNT(r.id)` 함수가 Null 데이터 개수를 0으로 올바르게 카운팅한 결과입니다.
      * **INNER JOIN 실행 시 대참사**:
        만약 이 자리에 단순 `INNER JOIN`을 사용했다면 'Java의 정석'은 RENTAL 데이터가 아예 없기 때문에 교집합 조건에 탈락되어 결과 셋에서 통째로 **증발**합니다. 그렇게 되면 도서관 관리자는 자신이 'Java의 정석'이라는 책을 보유하고 있는지조차 통계 화면에서 알 수 없게 됩니다.

* **GROUP BY와 집계 함수(COUNT, SUM, AVG)가 어떻게 동작하는지 쿼리 결과를 보며 이야기할 수 있는가?**
  * **모범 답안**:
    `GROUP BY`와 집계 연산은 임의의 원시 행 데이터셋을 특정 기준 속성에 맞춰 분류하고 통계를 계산하여 단일 대표 행으로 응축하는 연산입니다. RDBMS 엔진은 이 과정을 **[파티셔닝(Grouping) -> 독립 집계(Aggregating) -> 결합(Combining)]**이라는 3단계 파이프라인으로 수행합니다.
    - **실증 쿼리 (queries.sql:L196-203)**:
      ```sql
      SELECT c.name, COUNT(b.id) AS book_count, ROUND(AVG(b.price), 1) AS average_price
      FROM BOOK b
      INNER JOIN CATEGORY c ON b.category_id = c.id
      GROUP BY c.id, c.name;
      ```
    - **엔진 내부 연산 프로세스**:
      1. **원시 가상 릴레이션 빌드**: `FROM BOOK b JOIN CATEGORY c`가 작동하여, 개별 책의 행에 장르 이름 텍스트가 조인되어 붙은 중간 상태의 결과 집합을 임시 메모리에 구성합니다.
      2. **그룹핑 단계**: 데이터베이스 엔진은 지정된 그룹키인 `c.id`와 `c.name`을 활용하여 해시 테이블을 생성하고, 동일한 장르 키를 가진 도서 행들을 독립된 메모리 상자(Bucket) 속으로 각각 분류해 밀어 넣습니다.
         * *'컴퓨터과학' 버킷*: [밑바닥 딥러닝(28,000원), 클린 코드(33,000원), Java의 정석(32,000원)] 행이 분할 적재됨.
         * *'역사' 버킷*: [사피엔스(22,000원), 총균쇠(28,000원)] 행이 분할 적재됨.
      3. **집계 단계 (상자별 단일행 축약)**: 각 버킷 내부 데이터만을 고립적으로 바라보며 계산 연산을 집행합니다.
         * *'컴퓨터과학' 버킷 내부*:
           - `COUNT(b.id)` -> 버킷 안의 도서 인스턴스 갯수를 집계해 `3` 도출.
           - `AVG(b.price)` -> 세 도서의 평균 정가 $(28000+33000+32000)/3 = 31000.0$을 연산하여 `31000.0` 도출.
         * *'역사' 버킷 내부*:
           - `COUNT(b.id)` -> 도서 갯수 `2` 도출.
           - `AVG(b.price)` -> 평균가 $(22000+28000)/2 = 25000.0$ 도출.
      4. **결합 단계**: 각 버킷당 한 줄씩 도출된 요약값 행 `[컴퓨터과학, 3, 31000.0]`과 `[역사, 2, 25000.0]`을 최종 응답 테이블 형식으로 합쳐서 반환합니다.

### 항목 4: 복잡한 문제 해결 사례 분석 (Advanced Problem Solving & Optimization)

* **작성한 쿼리 중 가장 복잡했던 쿼리를 선택하고, 어떻게 풀었는지 단계별로 설명할 수 있는가?**
  * **모범 답안**:
    이번 과제 수행 중 비즈니스 요구사항 해석과 실행 성능 최적화 관점에서 가장 정교하게 설계된 두 개의 쿼리를 분석합니다.

    ### 1. Query 13: `NOT EXISTS` 상관 서브쿼리를 통한 휴면 회원 조회 (queries.sql:L267-274)
    ```sql
    SELECT id, name, email, join_date
    FROM MEMBER m
    WHERE NOT EXISTS (
        SELECT 1 
        FROM RENTAL r 
        WHERE r.member_id = m.id
    );
    ```
    * **단계별 논리 처리 흐름**:
      1. **외부 루프 스캔**: 메인 쿼리가 `MEMBER` 테이블(m)을 순차적으로 탐색합니다.
      2. **상관 관계 바인딩**: 현재 스캔 중인 특정 회원 인스턴스의 PK값인 `m.id`를 내부 서브쿼리 내부로 주입합니다.
      3. **Early Exit 기법을 활용한 존재 판별**: 서브쿼리는 `RENTAL` 테이블에서 외부에서 주입된 회원 ID와 일치하는 대여 내역이 있는지 조회합니다. 이때 옵티마이저는 매칭되는 대여 기록을 **단 1개**라도 찾는 그 즉시 나머지 검색을 전부 포기하고 즉시 `참(True)`을 리턴하는 **'Early Exit(조기 조절)'** 최적화 작동을 보장합니다.
      4. **부정 필터링**: `NOT EXISTS`에 의해 서브쿼리 결과가 존재하지 않는(공집합인) 회원, 즉 대여 기록이 한 번도 없는 휴면 회원만 선별되어 메인 쿼리의 SELECT 프로젝션을 통과합니다.
    * **성능 아키텍처 관점의 깊이 (NOT EXISTS vs LEFT JOIN ... WHERE NULL)**:
      휴면 회원을 찾기 위해 흔히 `MEMBER m LEFT JOIN RENTAL r ON m.id = r.member_id WHERE r.id IS NULL` 구조를 작성하곤 합니다. 하지만 대여 기록의 볼륨이 수억 건일 때, 이 방식은 데이터 전체를 읽어 거대한 메모리 영역에서 조인을 시도하므로 과도한 Temp DB 부하를 줍니다. 반면 `NOT EXISTS` 상관 서브쿼리는 인덱스를 타고 매칭 한 건만 발견되면 즉시 탐색 노드를 탈출(Early Exit)하므로 디스크 I/O 소모량을 급격히 절감시켜 고성능 데이터베이스 아키텍처에 훨씬 적합합니다.

    ### 2. Query 14: Date 내장 함수와 Julian Day 연산을 통한 연체 상태 일괄 업데이트 (queries.sql:L292-296)
    ```sql
    UPDATE RENTAL
    SET status = 'OVERDUE'
    WHERE return_date IS NULL 
      AND status = 'RENTED'
      AND (julianday('2026-05-24') - julianday(rental_date)) > 14;
    ```
    * **단계별 처리 메커니즘**:
      1. **상태 필터링**: RENTAL 테이블에서 아직 책을 돌려주지 않았고(`return_date IS NULL`) 현재 정상 대여 중인(`status = 'RENTED'`) 데이터 블록을 1차 격리합니다.
      2. **Julian Day 날짜 수치 변환**: SQLite의 `julianday()` 함수는 지정된 ISO-8601 문자열 날짜를 율리우스 일(Julian Day, 소수점을 포함한 연속적인 날 수 지표)로 계산합니다. 이를 통해 '2026-05-24'와 대여일 `rental_date`를 수치형으로 변환합니다.
      3. **경과 기한 판별 및 갱신**: 두 율리우스 일의 차이가 14일을 초과한 데이터 행만 타겟팅하여 `status` 값을 'OVERDUE'로 벌크 갱신하는 트랜잭션을 실행합니다. 이로 인해 수동 관리 없이 배치 시스템 등에서 실시간 연체 갱신을 정확하게 처리할 수 있습니다.

* **미션 수행 중 가장 어려웠던 부분과 해결 방법을 구체적으로 말할 수 있는가?**
  * **모범 답안**:
    이번 데이터 모델링 과제에서 직면했던 가장 높은 엔지니어링적 진입 장벽은 **외래키 제약조건의 연쇄 참조 정책(Referential Action) 설계와 서비스 탈퇴 시 발생하는 트랜잭션 역사성 손실 문제**였습니다.
    * **고민과 설계 딜레마 (CASCADE의 물리적 위험성)**:
      - 본 프로젝트의 `MEMBER` - `RENTAL` 관계에서는 부모인 회원이 탈퇴(DELETE)될 시 `ON DELETE CASCADE` 옵션을 통해 그의 대여 정보들이 데이터베이스에서 자동으로 동반 삭제되도록 작성하였습니다.
      - 그러나 이는 학습 환경을 넘어선 실제 기업의 운영용 RDBMS 환경에서는 **치명적인 설계적 재앙**입니다. 대여 이력 데이터는 기업의 매출 현황, 도서 유실 보상 처리, 대여 빈도 기반 도서 구매 예산 책정 등 회계 및 통계와 얽힌 귀중한 트랜잭션 자산이기 때문입니다. 단 한 명의 회원이 탈퇴했다고 해서 그의 대여 내역을 데이터베이스에서 완전히 삭제(Hard Delete)해 버리면, 연간 통계 결산 시 수치가 어긋나는 정합성 파괴가 발생합니다. 그렇다고 `ON DELETE RESTRICT`를 지정하면, 대여 이력이 한 개라도 남아있는 회원은 탈퇴 처리가 영구히 차단되어 고객 컴플레인을 받게 됩니다.
    * **엔지니어링적 대안 설계 (Soft Delete 패턴 적용)**:
      - 이 문제를 해결하기 위해 물리적인 행 삭제 연산(`DELETE`)을 사용하는 대신, 논리적 상태 갱신 방식인 **소프트 딜리트(Soft Delete)** 패턴의 필요성을 학습했습니다.
      - 테이블에 `is_active` (활성화 플래그, 1/0) 또는 `member_status` ('ACTIVE', 'WITHDRAWN') 컬럼과 함께 `withdrawn_at` (탈퇴 일시) 컬럼을 새롭게 설계에 배정합니다.
      - 회원이 서비스 탈퇴를 요청할 시, 실제 DELETE 쿼리를 던지는 대신 `UPDATE MEMBER SET member_status = 'WITHDRAWN', withdrawn_at = CURRENT_TIMESTAMP WHERE id = ?;` 쿼리를 수행합니다.
      - 이 방식을 취하면 회원의 로그인 등 서비스적 접근은 논리적으로 완전 통제하면서도, 외래키 관계가 맺어진 `RENTAL` 테이블의 과거 대여 이력은 단 한 건도 손실되지 않고 온전히 유지되므로 트랜잭션의 정합성과 과거 데이터의 역사성을 완벽하게 지킬 수 있습니다.
